# Collateral contracts

Solidity contracts for the CDM collateral prototype, built with **Hardhat 3** (viem). They are the on-chain layer of
the prototype architecture (`../architecture/prototype.architecture.json`): the margin call contract, the collateral
control contract, the repo, securities loan, triparty and CCP contracts, the tokenized collateral tokens, the oracle
feed, the record keeper register and the provenance anchors. Part of `task-e2e-wiring`.

## Contracts

| Contract | Role |
|---|---|
| `OracleFeed.sol` | Price (scaled 1e8) and default feed. Only the publisher (the market operator's key) may write; every service reads valuations and default status here. |
| `TokenizedCollateral.sol` | ERC-20 collateral token, 0 decimals (whole units), carrying ISIN / CUSIP / DTI identifiers (`concept-asr-onchain-asset-identity`). Dev-only unrestricted `mint`. |
| `MarginCall.sol` | Margin call lifecycle: issue, respond (agree / partial / dispute), propose collateral, decide (`wp-adr-margin-call-state-onchain`). Each state change is made by exactly one party's key. Every lifecycle step anchors its CDM document by a keccak-256 `cdmHash` on its event — `CallIssued`, `CallAnswered`, `CollateralProposed`, `ProposalDecided`, `CallSettled`, `CallWithdrawn`, `CancellationRequested`, `CancellationDecided` (`concept-asr-onchain-call-state`, ADR `wp-adr-cdm-payload-carrier`); cancellation (`flow-call-cancellation`): `withdrawCall` by the caller while the call is issued, `requestCancellation` by either party once it is answered and not settled, `decideCancellation` by the other party; a pending request blocks proposals, decisions and settlement, and acceptance sets the call `Cancelled` and its live proposal `Cancelled`; replacement (`flow-call-replacement`): `issueReplacementCall` issues a call that replaces a cancelled one with the same caller, called party and kind, records `replaces` and `replacementOf` (one replacement per cancelled call) and emits `CallReplaced`; the document itself lives in the off-chain payload store (`../store`). Settlement is marked by the control contract (`markSettled`, called from `pledge`, `settleByTransfer`, `returnCollateral` and `returnByTransfer` with the settle step's `cdmHash`). |
| `CollateralControl.sol` | Settlement against the margin call state and oracle feed. Initial margin is escrowed here and leaves only by return, enforcement, close-out or substitution (`wp-adr-im-segregation`); `enforce(callId, cdmHash)` takes and emits the hash of the CDM `CollateralEnforcement`, so an Enforcement `LedgerAnchor` can be built (`task-authoritative-record-settlement-enforcement`); variation margin passes title directly. `closeOut` (after the pledgor's default on the feed, secured party key) applies whole units of the escrow, in the order first pledged, to the Early Termination Amount owed and returns the surplus (G15). `requestSubstitution` / `decideSubstitution` / `settleSubstitution` substitute escrowed items under ISDA CSA Paragraph 4(d): the originals must be in escrow, the substitute eligible and worth at least as much after haircuts (checked again at settlement), and the secured party's consent is always required (G16). `stateInterest` (secured party) records the Interest Amount on the pledgor's cash collateral for one period with the CDM statement's hash and pays a positive amount to the pledgor in the same transaction; the cash token must be eligible with no haircut; a negative amount is paid by the pledgor with `payInterest` (G17). `proposeAmendment` / `decideAmendment` amend a pair's terms (`flow-agreement-amendment`): either party proposes haircut terms with the CDM amendment hash, chained from the pair's `agreementHash`, one pending at a time; on the other party's consent the global schedule is copied for the pair on its first amendment, the terms apply, and `agreementHash` becomes the amendment hash. Election changes (MTA, rounding) travel in the CDM document and are applied by the services. Pledge checks value-after-haircut ≥ agreed, using the oracle price and the pair's eligibility (`eligibilityFor`: the global schedule until the pair's first amendment). Settlement netting (`flow-settlement-netting`): `settleNetted` settles agreed VM calls (accepted proposal of the cash token alone), agreed return calls (agreed amount in the cash token at the feed price) and Interest Amounts held by `stateInterestForNetting` between two parties in one transaction, by one transfer of the net from the calling key, which must owe it; `nettedIn` records the netting per call and statement and `SettlementNetted` the net. |
| `PortfolioReconciliation.sol` | Portfolio reconciliation between two parties (`flow-reconciliation`, `wp-adr-reconciliation-scope`). `commitSnapshot` records the hash of a party's trade snapshot; the snapshots themselves go service to service. `commitResult` records, once per party and run, the hash of the reconciliation result and its break count; the run (`reconciliationIdOf` the two snapshot ids) becomes `Agreed` when both result hashes match and `Disagreed` otherwise. No trade data is on-chain. Kept separate from `CollateralControl.sol`, which is close to the EIP-170 size limit. |
| `RepoSettlement.sol` | Term repo under the GMRA, settled delivery versus payment (`flow-repo-purchase-repurchase`, `wp-adr-repo-purchase-repurchase`). `book` (the seller) records the buyer, the security and quantity, the cash token, the Purchase Price, the Repurchase Price and the hash of the CDM trade; `affirm` (the buyer) must carry the same hash. `instruct` records each party's instruction for the purchase (after affirmation) or the repurchase (after the purchase) with the hash of the CDM settlement document; the second instruction must carry the same hash and moves both legs in one transaction by `transferFrom` against each party's approval: at the purchase the securities to the buyer and the Purchase Price to the seller, at the repurchase both back at the Repurchase Price. No dates are checked on-chain. Kept separate from `CollateralControl.sol`. |
| `SecuritiesLoan.sol` | Securities loan under the GMSLA (`flow-gmsla-loan-delivery-return`, `wp-adr-gmsla-loan-delivery-return`). `book` (the lender) records the borrower, the loaned token and quantity, the collateral token and amount, and the hash of the CDM loan; `affirm` (the borrower) must carry the same hash. `instructDelivery` records each party's instruction with the hash of the CDM delivery document; the second, with the same hash, moves the securities to the borrower and the collateral to the lender in one transaction. `instructReturn` takes the quantity returned, the collateral redelivered and the hash of the CDM return document, which both parties must state the same; the second moves both back, reduces the loan and makes the hash the trade hash. A return of the whole outstanding quantity returns the loan and must redeliver all the collateral. Collateral passes by title transfer: the contract holds no tokens. No dates are checked on-chain. `recall` (the lender, `flow-gmsla-recall`, `wp-adr-gmsla-recall`) records one pending recall of all or part of an open loan: the quantity, the intended settlement date (YYYYMMDD) and the hash of the CDM recall notice. `withdrawRecall` removes it with the hash of the withdrawal. A settled return reduces the quantity still recalled and clears the recall when it returns at least as much. The due date is not enforced on-chain. `requestSubstitution` (the borrower, `flow-gmsla-substitution`, `wp-adr-gmsla-substitution`) records one pending substitution of all the collateral of an open loan: the substitute token, its quantity and the hash of the CDM substitution document; none while a return is pending, and no return is instructed while it is pending. `agreeSubstitution` (the lender, the same hash) moves the substitute to the lender and all the collateral held back to the borrower in one transaction, and makes the hash the trade hash; `refuseSubstitution` (the lender) clears it. `bill` (a party of an open or returned loan, `flow-gmsla-rebate`, `wp-adr-gmsla-rebate`) records one pending invoice: the cash token, the period end (YYYYMMDD, after the billed-through date), the amount and the hash of the CDM invoice. `payBill` (the other party, the same hash) moves the amount in the stored cash token from it to the biller and sets the billed-through date to the period end; `refuseBill` (the payer) clears it. The period and the amount are checked by the services. |
| `TripartySettlement.sol` | Triparty repo between a collateral giver, a receiver and the agent BANK-T (`wp-adr-triparty-terms-profile` and the triparty ADRs that follow it): terms proposed by hash and affirmed by the receiver and the agent; the giver's deposits and withdrawals with its ranking; repo request, the agent's allocation, purchase settlement, revaluation, substitution, trade end and the agent's reports, each with the hash of its cdm-ext document. |
| `CcpClearing.sol` | CCP clearing of `RepoSettlement` repos by BANK-C (`wp-adr-ccp-scope`): the rulebook, members and default fund; clearing by novation; daily variation and initial margin rounds; member default with the default fund waterfall; porting. |
| `RecordKeeperRegister.sol` | The record keeper's confirmations for a token whose authoritative record is kept off the ledger (Registered or Claim; tMMF in the prototype). The record keeper (the transfer agent in `../services/oracle`, mkt key) calls `confirm(txHash, token, ref)` once its own register shows the token movements of a ledger transaction, emitting `RegisterConfirmed`; any other key reverts `NotRecordKeeper`. Interim rules REG-1, REG-2 and REG-4: a Registered or Claim transfer or enforcement is complete only after this confirmation (`task-authoritative-record-settlement-enforcement`). |
| `ProvenanceAnchors.sol` | Token-level provenance anchors (`task-document-provenance`, `wp-adr-document-provenance`). `anchor(token, linkId, cdmHash, revisionOf)` emits `ProvenanceAnchored` for a PROV-O link record kept off the ledger (issuance record, token terms, custody record or register statement, constitution, valuation, control agreement, registry entry), hashed with keccak-256 over its JCS canonical form. One chain of revisions per link: a revision must name the link's current head. Any account may anchor; the record keeper's authority comes from its Verifiable Credential, which the collateral service verifies. |
| `CollateralTypes.sol` | Shared enums and structs, mirroring the CDM lifecycle in `../cdm-ext`. |

## Test balances

`scripts/deploy.ts` mints the parties' free balances from `scripts/test-balances.json`. The live specs move value from
the pledgor to the secured party, so `scripts/live-e2e.sh check` first runs `scripts/top-up-test-balances.mjs`, which
mints each party's shortfall back to those targets with the tokens' dev-only `mint` (`task-live-test-balances`).
Escrowed collateral is left as it is.

## EVM target

The Besu genesis activates **Berlin + London only** (no Shanghai), so the EVM has no `PUSH0`. `hardhat.config.ts` pins
`evmVersion: "london"`; the solc default (`cancun`) would emit `PUSH0`/`MCOPY`, which revert as invalid opcodes on this
chain.

The contracts compile with `viaIR: true` (optimizer, 200 runs). With `settleNetted` (`flow-settlement-netting`) the
legacy pipeline put `CollateralControl` over the 24,576-byte contract size limit (EIP-170): 24,906 bytes at 200 runs,
24,614 at 1 run. Through the IR pipeline it is 20,063 bytes.

## Build, test, deploy

```bash
npm ci
npm run build          # hardhat compile (solc 0.8.28, london target)
npm test               # 147 unit and property tests on the in-memory EDR network (run 2026-11-22)
npm run deploy:besu    # deploy to the running Besu network, write deployments/besu.json
```

`deploy:besu` runs `scripts/deploy-besu.mjs`, which reads the market operator's node key (`../besu/mkt/data/key`) and
signs as the mkt account — the deployer and the oracle publisher. The chain is zero-base-fee (`gasPrice 0`), so no
account needs funding. Opening balances, prices and haircuts mirror `../console/src/domain/reference.ts` and
`scenarios.ts`, so the live stack starts where the mocked console did.

### `deployments/besu.json`

The address registry the gateway, services and console read: chain id, RPC URLs per node, party addresses, the oracle
publisher, the contract addresses (`contracts.recordKeeperRegister` and `contracts.provenanceAnchors` were added after
`v0.1-demo`; a deployment made before them has neither and needs a reset), the price scale, and per-token address / decimals / haircut / identifiers, with
`authoritativeRecord`, `recordKeeper` and `controlAgreement` for a Registered or Claim token (tMMF: "MMF Transfer
Agent", control agreement `CA-TMMF-2026-01`) and `provenanceRequired` for tUST and tMMF.
Written on every deploy; not committed (it is environment state).
